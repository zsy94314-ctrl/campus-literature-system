# AI 辅助交互记录

## 1 说明

本项目在需求分析、技术路线讨论、代码建议、问题排查、测试用例设计和文档整理过程中使用了 AI 工具辅助。AI 的作用是提供思路、生成初稿、辅助定位问题和整理材料；最终方案取舍、代码整合、本地运行测试、功能验收和报告定稿由人工完成。

本文档只记录交互主题摘要，不粘贴超长聊天原文，不包含真实 API Key、数据库密码、Token 等敏感信息，也明确保留人工设计、整合、测试和验收责任。

## 2 AI 辅助范围

| 阶段 | AI 辅助内容 | 人工确认内容 |
|---|---|---|
| 需求分析 | 梳理普通用户、管理员、backend-ai 三类功能边界 | 确认最终功能范围和课程要求 |
| 技术路线 | 讨论 React、Spring Boot、MySQL、FastAPI、sentence-transformers、FAISS 的组合方案 | 选择前后端分离和 Python 智能检索服务 |
| 数据库设计 | 建议用户、文献、分类、收藏、综述记录、LLM 配置等表结构 | 对照 SQL 脚本执行和字段修正 |
| 智能检索 | 讨论语义召回、主题画像、Query Expansion、MySQL 补充召回、finalScore、matchReason | 根据实际检索结果调整主题词、分类权重和降权逻辑 |
| 综述生成 | 讨论离线规则生成、在线 LLM 增强、参考文献校验和降级机制 | 运行本地服务，检查生成内容和记录字段 |
| LLM API 管理 | 建议配置表、脱敏展示、active 切换和连接测试流程 | 管理员页面和接口联调 |
| 问题排查 | 辅助定位分类统计、分类跳转、跨学科跑偏、LLM 截断等问题 | 人工修改代码并测试验证 |
| 测试用例 | 生成覆盖主流程、异常流程和权限控制的测试表 | 人工执行或补充实际结果 |
| 文档整理 | 辅助整理 README、接口文档、数据库设计、测试文档和报告初稿 | 对照代码、SQL 和页面实际功能确认 |

## 3 典型交互摘要

### 3.1 需求分析

交互主题：

- 校园学术文献智能检索与综述生成系统应包含哪些功能。
- 普通用户与管理员的权限如何区分。
- 智能检索、相似推荐、综述生成之间如何形成完整流程。

AI 辅助结果：

- 整理出用户注册登录、文献普通检索、高级检索、智能语义检索、详情查看、收藏、相似推荐、智能推荐参考文献、综述生成、综述记录、管理员后台、LLM API 管理等模块。

人工处理：

- 根据课程时间和实现难度确定最终范围，没有将 PDF 上传、真实论文库、Docker、流式输出、Cross-Encoder Rerank 写入已实现功能。

### 3.2 技术路线讨论

交互主题：

- 是否将智能检索独立为 Python 服务。
- 如何在 Java 后端和 Python 语义检索服务之间通信。
- 在线 LLM 是否应作为系统唯一生成方式。

AI 辅助结果：

- 建议采用 `frontend`、`backend-java`、`backend-ai`、`database` 分层。
- 建议 Spring Boot 作为主业务后端，FastAPI 作为语义检索服务。
- 建议保留离线综述生成作为默认稳定模式，在线 LLM 作为增强模式。

人工处理：

- 落地为 React + Spring Boot + MySQL + FastAPI + FAISS 的架构。
- 明确在线 LLM 不可用时必须自动降级。

### 3.3 智能检索优化

交互主题：

- 纯 FAISS 语义检索在跨学科查询中跑偏。
- 如何让“人工智能在医学中的应用”“大学生心理健康智能预警”“人工智能在农业中的应用”等查询更贴近目标学科。

AI 辅助结果：

- 提出多学科主题画像。
- 提出 Query Expansion 查询扩展。
- 提出 MySQL 关键词补充召回。
- 提出 `keywordScore`、`categoryScore`、`weakPenalty` 和 `finalScore` 综合重排。
- 建议返回 `matchReason` 说明推荐原因。

人工处理：

- 在 `AiServiceImpl` 中实现主题画像和重排逻辑。
- 根据实际分类体系确认主题范围：教育、医学健康、心理健康、文献检索、农业生态、法学治理、经济管理、人文艺术、工程技术、自然科学、人工智能通用主题。

### 3.4 综述生成升级

交互主题：

- 早期综述生成过于模板化、像摘要拼接。
- 如何从所选文献中归纳研究方向、问题和趋势。

AI 辅助结果：

- 建议按主题识别、关键词提取、研究方向分配、问题池、趋势池生成结构化综述。
- 建议输出六部分：研究背景、研究现状、主要研究方向、存在问题、发展趋势、参考文献来源。

人工处理：

- 在 `ReviewRecordServiceImpl` 中实现离线规则生成。
- 通过用户选择的 2 到 5 篇文献构造参考来源。

### 3.5 LLM 增强综述生成

交互主题：

- 用户端支持离线和在线两种综述生成。
- 管理员端维护 DeepSeek / OpenAI-compatible API。
- 如何避免 LLM 编造参考文献。

AI 辅助结果：

- 建议新增 `llm_config` 表。
- 建议 `ReviewGenerateRequest` 使用 `mode` 区分 `rule` 和 `llm`。
- 建议 `review_record.generation_mode` 记录 `rule`、`llm`、`llm_fallback_rule`。
- 建议前端只展示脱敏 API Key。
- 建议 LLM 输出后由后端补全参考文献并清理非法引用编号。

人工处理：

- 实现 `LlmConfigController`、`LlmConfigServiceImpl`、`LlmReviewServiceImpl`。
- 管理员页面实现新增、编辑、删除、active、测试连接和长文本测试。
- 用户端综述记录页面显示 generationMode 标签和筛选。

### 3.6 问题排查

AI 辅助定位并形成修复思路的问题包括：

| 问题 | 修复摘要 |
|---|---|
| 首页分类统计为 0 | 改为后端按全部文献和二级分类真实聚合 |
| 首页分类跳转不生效 | 跳转传 `categoryId`，搜索页监听 URL 参数自动检索 |
| 智能检索跨学科跑偏 | 增加主题画像、Query Expansion、MySQL 补充召回和 `finalScore` |
| 综述生成模板化 | 增加主题识别、关键词提取、研究方向归纳、问题与趋势生成 |
| LLM 输出截断 | 检查 `finish_reason`，必要时提高 `max_tokens` 重试，失败降级 |
| LLM 参考文献不完整 | 后端强制补全或替换第六节“参考文献来源” |
| 第六节参考文献被误判为截断 | 截断检查与参考文献补全分离，前五节完整即可补全第六节 |
| LLM 产生不存在的引用编号 | 后端正则清理超出所选文献范围的引用编号 |

## 4 AI 参与边界

- AI 可辅助提出方案、生成草稿、解释报错、整理测试用例和文档。
- AI 不能替代人工架构决策、课程验收和最终责任。
- AI 生成内容必须经过人工审核。
- 是否功能完成，以本地服务启动、接口返回、页面操作和数据库结果为准。
- 真实 API Key、数据库密码、Token 不写入 AI 对话、文档或代码仓库。
- 文献数据是课程项目模拟数据，不能因 AI 文档措辞而写成真实论文库。

## 5 人工完成与验收内容

人工完成内容包括：

- 确定选题和功能范围。
- 安装和配置 MySQL、JDK、Maven、Node.js、Python 等环境。
- 执行数据库脚本并导入模拟文献数据。
- 启动和联调 backend-ai、backend-java、frontend。
- 测试普通检索、高级检索、智能检索、相似推荐、收藏、综述生成和管理员后台。
- 在管理员后台配置 LLM API，并验证在线生成、离线生成、自动降级三种流程。
- 检查 `generationMode=rule`、`generationMode=llm`、`generationMode=llm_fallback_rule` 的前端显示和数据库保存。
- 检查 LLM 参考文献是否只来自用户选择的文献。
- 整理最终报告、截图、测试记录和答辩材料。

## 6 风险与改进

| 风险 | 控制方式 |
|---|---|
| AI 生成文档可能与代码不一致 | 以代码和 SQL 为准逐项核对 |
| LLM 在线生成不稳定 | 保留离线规则生成，异常时降级 |
| LLM 可能编造引用 | 后端补全参考文献并清理非法引用 |
| 向量检索跨学科泛化 | 主题画像、扩展词、MySQL 补充召回和弱相关降权 |
| API Key 泄露 | 前端脱敏，文档不写真实 Key，生产环境建议加密和审计 |

后续可改进方向：

- API Key 加密存储。
- 语义检索增加 BM25 混合召回和 Rerank。
- 在线 LLM 增加流式输出。
- 接入真实论文库和 PDF 解析。
- 增加更严格的引用格式校验。

## 7 小结

AI 在本项目中承担辅助分析、初稿生成和问题排查角色。最终系统功能、代码整合、运行测试和验收由人工完成。通过 AI 辅助提高了开发和文档整理效率，但所有结论均以当前项目真实代码、SQL 脚本和本地运行结果为准。
