PROJECT BACKGROUND
03 / 21
01 · 项目背景与目标
校园学习场景正在从“查资料”走向“组织知识”
在课程论文、科研训练和毕业设计准备中，学生需要完成检索、筛选、收藏、归纳和综述写作。传统关键词检索能解决“找得到”，但不能很好解决“找得准、讲得清、引用可追溯”。
01

主题表达更自然

学生更习惯输入“人工智能在医学中的应用”这类自然语言主题。

02

跨学科判断更复杂

教育、医学、心理、工程等主题经常交叉，简单关键词容易跑偏。

03

综述必须有依据

LLM 不能脱离本地文献材料自由生成，参考文献必须被后端校验。

01 · 用户痛点与核心目标
目标不是做真实论文平台，而是完成可运行的软件工程闭环

普通用户端

注册登录、普通检索、高级检索、智能检索、文献详情、收藏、相似推荐、综述生成和历史记录。

管理员端

文献管理、分类管理、用户管理、真实数据统计、重建智能索引和 LLM API 管理。

智能检索服务

backend-ai 使用 sentence-transformers 和 FAISS 语义召回，Spring Boot 负责业务重排。

综述生成闭环

离线 rule 默认稳定，在线 llm 增强表达，失败时自动降级为 llm_fallback_rule。

FEASIBILITY
05 / 21
02 · 可行性研究与竞品分析
技术、经济、操作三方面均适合课程项目实现

技术可行

React、Spring Boot、MySQL、FastAPI、FAISS 均成熟可用；前后端分离降低联调复杂度。

经济可行

基础功能本地运行；DeepSeek API 只用于在线增强与连接测试，离线 rule 模式不产生外部调用费用。

操作可行

用户按“检索—选择—生成—记录”操作；管理员按“维护数据—重建索引—管理 LLM 配置”操作。

可行性结论：系统的价值在于以可控成本实现从需求分析、设计、编码、测试到维护的完整工程过程。

不与大型论文库比资源规模，而突出工程闭环和受约束生成

通用 LLM语言表达能力强，生成速度快容易脱离材料生成，引用来源不稳定采用 RAG 风格流程，参考文献由后端补全或替换
本系统检索、推荐、生成、记录、管理一体化数据为课程模拟数据，规模有限更适合展示软件工程课程中的设计、实现和测试过程

NON-FUNCTIONAL REQUIREMENTS
09 / 21
03 · 非功能需求
除“能用”之外，还要保证可靠、安全、可维护

性能

普通检索快速响应，智能检索允许向量召回和重排带来的适度延迟。

可靠性

backend-ai 或 LLM 不可用时，基础检索和离线综述仍能继续使用。

安全性

区分普通用户和管理员权限，LLM API Key 前端脱敏展示，文档不写真实密钥。

可维护性

前端、主后端、AI 服务和数据库脚本分离，便于定位问题和扩展功能。

SEARCH ALGORITHM
16 / 21
06 · 详细设计与编码实现
智能检索不是简单 FAISS 召回，而是语义召回与业务重排结合

关键算法流程

1
backend-ai 通过 sentence-transformers 向量化，FAISS 召回候选文献。
2
Spring Boot 扩大 recallTopK，并识别教育、医学、心理、工程等主题画像。
3
Query Expansion 与 MySQL 关键词补充召回后，按 finalScore 重排并输出 matchReason。

RAG REVIEW GENERATION
17 / 21
06 · 检索增强式综述生成
采用 RAG 思想：先检索材料，再基于选中文献生成综述

双模式生成

  • rule：默认稳定模式，不依赖外部 API
  • llm：在线增强模式，调用管理员 active 配置
  • llm_fallback_rule：在线失败后自动降级
  • 参考文献必须来自用户选择的文献

06 · LLM 输出校验与降级机制
工程重点不是“调用模型”，而是控制模型输出边界

校验点
